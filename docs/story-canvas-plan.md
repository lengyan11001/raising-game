# 剧本画布产品规划 v0.1

## 1. 产品结论

把“一个剧本 = 一个项目”作为聚合根；画布只负责编排和展示，业务数据全部落 PostgreSQL。

一条完整生产链固定为：

`原始文稿 → 定稿版本 → LLM 拆集/拆场 → 角色/场景/道具资产计划 → 分镜计划 → 最终提示词 → 关键帧图 → 视频镜头 → 审核/导出`

核心原则：

1. 画布不是数据仓库。节点只保存 `assetId`、`shotId`、`promptVersionId` 等引用。
2. 所有可生成内容都版本化；上游变化后，下游自动标记 `stale`，不静默覆盖。
3. 文本也是正式资产，必须有版本、审批状态和可追溯来源。
4. 不做一个巨大的画布。采用“项目画布 → 单集画布 → 单镜头画布”三层，规避现有 100 节点/200 连线限制。
5. 图片、视频文件可存对象存储；其元数据、归属、版本、生成记录必须入库。

## 2. 标准剧本流程

### 阶段 A：文稿定稿

- 导入/粘贴原始剧本。
- 保存为 `script_version`，支持草稿、定稿、废弃。
- 定稿后锁定内容；修改必须产生新版本。

### 阶段 B：LLM 自动拆解

一次拆解输出结构化结果，分块处理，避免单次上下文过大：

- 项目级：题材、受众、单集时长、集数、整体风格、视觉基调。
- 剧集级：每集标题、梗概、钩子、冲突、结尾悬念。
- 场景级：场景编号、地点、时间、人物、剧情目的。
- 角色级：角色档案、关系、外形锚点、服装、表情。
- 资产级：角色、场景、道具、风格参考。
- 镜头级：镜号、景别、机位、动作、台词、时长、转场。

每层都要人工确认后，才允许进入下一层。

### 阶段 C：资产计划与生成

先产出“资产清单”，再生成素材。角色和场景不能直接从文字一把生成，必须先生成稳定设定卡，再生成多视图/多状态参考图。

### 阶段 D：分镜与提示词

每集拆为镜头表。每个镜头至少包含：

- 剧情信息：镜号、场景、角色、动作、对白、时长。
- 图像提示词：角色引用、场景引用、构图、光线、镜头。
- 视频提示词：动作、运镜、节奏、首尾帧、负面约束。
- 最终提示词快照：冻结后用于生成，不允许隐式跟随上游变化。

### 阶段 E：图像与视频生成

- 镜头可先出关键帧图，再图生视频；也可直接文生视频。
- 每次生成产生 `generation_record`，绑定镜头、提示词版本、引用资产版本。
- 失败、重试、采用、淘汰都要可追溯。

### 阶段 F：审核与导出

- 镜头级：待生成、生成中、待审、通过、重做。
- 集级：是否齐镜、是否齐音、是否可导出。
- 项目级：总资产数、完成率、缺失资产、生成成本。

## 3. 领域模型

### 3.1 核心对象

| 对象 | 说明 |
|---|---|
| `story_project` | 一个剧本项目，聚合根 |
| `script_version` | 原始文稿或拆解后剧本版本 |
| `episode` | 单集 |
| `story_asset` | 角色、场景、道具、风格、声音等逻辑资产 |
| `asset_variant` | 角色服装/表情、场景时段/角度等变体 |
| `shot` | 单镜头 |
| `prompt_version` | 图片/视频最终提示词版本 |
| `generation_ref` | 生成记录与资产/镜头/提示词版本的关联 |
| `canvas_scope` | 项目、剧集、镜头对应的画布范围 |

### 3.2 状态机

资产：

`draft → planned → generating → review → approved → stale → archived`

镜头：

`draft → planned → image_ready → video_generating → video_ready → approved → rework`

版本：

`draft → frozen → superseded`

冻结后生成产物必须引用具体版本；上游变更只设置 `stale`，不自动改写已通过镜头。

### 3.3 资产复用

- 角色只建一次，跨集引用同一角色资产和指定变体。
- 场景按“地点 + 时段 + 角度”生成变体。
- 道具可按剧情重要性分为主道具和背景道具。
- 每个镜头只引用资产 ID，不复制角色/场景描述。

## 4. 画布节点设计

保留现有 `imageGenerate` 和 `unifiedVideoGen` 节点，新增以下站点节点：

| 节点 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `scriptInput` | 文本/文件 | 文本 | 导入原始剧本 |
| `scriptFinalize` | 文本 | 冻结文稿 | 形成定稿版本 |
| `episodePlanner` | 定稿文稿 | 剧集列表 | 判断集数、单集梗概 |
| `assetExtractor` | 剧集/文稿 | 角色/场景/道具清单 | 形成资产计划 |
| `characterCard` | 角色描述 | 角色设定卡 | 生成稳定角色锚点 |
| `sceneCard` | 场景描述 | 场景设定卡 | 生成场景锚点 |
| `shotPlanner` | 单集内容 | 镜头列表 | 拆分镜 |
| `promptComposer` | 镜头+资产引用 | 最终提示词 | 结构化拼装提示词 |
| `reviewGate` | 任意文本/媒体 | 通过或退回 | 人工审核卡点 |

节点端口需要区分类型：

- `text`
- `script`
- `episode[]`
- `asset[]`
- `shot[]`
- `prompt`
- `image`
- `video`

只允许同类型或显式声明可转换的端口相连，避免文本节点误接到图片输入。

## 5. 三层画布结构

### 项目画布

只放项目级流程：

`原始文稿 → 定稿 → 集数规划 → 角色/场景/道具计划 → 剧集卡片`

推荐 20～40 个节点。每个剧集卡片是进入单集画布的入口。

### 单集画布

只放当前集流程：

`单集剧本 → 分场 → 镜头列表 → 提示词批量生成 → 关键帧 → 视频生成 → 审核`

推荐 30～80 个节点。超过 80 时要拆“场次画布”。

### 单镜头画布

用于复杂镜头：

`镜头描述 → 引用角色/场景 → 图片提示词 → 关键帧 → 视频提示词 → 视频结果 → 采用版本`

推荐 8～20 个节点。

这样既符合现有画布上限，也避免用户在一个无限大的画布里失去上下文。

## 6. 一个剧到底需要多少资产

### 6.1 计算公式

设：

- `E` = 集数
- `C` = 有视觉设定的角色数
- `Vc` = 每角色平均变体数（服装、表情、阶段）
- `S` = 场景地点数
- `Vs` = 每场景平均变体数（时段、角度、天气）
- `P` = 道具资产数
- `K` = 总镜头数
- `I` = 每镜头平均关键帧图数
- `R` = 平均生成重试倍率

逻辑资产约为：

`1 项目 + E 集 + C×Vc 角色变体 + S×Vs 场景变体 + P 道具 + K 镜头 + K 提示词`

媒体文件约为：

`K×I 图片 + K 视频 + 生成重试`

### 6.2 三种规模

| 规模 | 集数 | 角色 | 场景 | 道具 | 镜头 | 图片生成量 | 视频生成量 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 单集样片 | 1 | 4 | 5 | 10 | 20～30 | 30～60 | 20～30 |
| 三集 MVP | 3 | 6 | 8～10 | 15～25 | 60～90 | 90～180 | 60～90 |
| 十集短剧 | 10 | 8～14 | 15～25 | 30～60 | 250～400 | 400～800 | 250～400 |
| 24 集短剧 | 24 | 12～20 | 30～50 | 80～150 | 650～1,000 | 1,000～2,000 | 650～1,000 |

十集、每集 60～90 秒的竖屏短剧，建议按以下基线估算：

- 6～8 个主要角色，4～6 个配角。
- 15～20 个主要场景，每个场景 2～3 个常用变体。
- 30～50 个剧情道具。
- 300 个左右镜头。
- 每个镜头 1～2 张关键帧候选。
- 图片生成 500～800 张，视频生成 300～450 条。
- 逻辑资产记录约 1,200～2,000 条，媒体文件约 800～1,200 个。

这里的“资产”要区分逻辑资产和媒体文件。真正需要用户管理的通常不是上千个文件，而是几十个角色/场景卡、几百个镜头和每镜头最终采用的版本。

## 7. 数据库与接口边界

新增业务表，不把剧本、资产和镜头塞进 `app_workflow_canvases.payload`：

- `app_story_projects`
- `app_story_script_versions`
- `app_story_episodes`
- `app_story_assets`
- `app_story_asset_variants`
- `app_story_shots`
- `app_story_prompt_versions`
- `app_story_generation_refs`
- `app_story_canvas_links`

现有 `app_workflow_canvases` 继续保存画布布局和节点引用；通过 `app_story_canvas_links` 关联项目、剧集或镜头。

API 分三层：

1. 项目与文稿：创建项目、导入文稿、冻结版本、启动拆解任务。
2. 资产与镜头：资产 CRUD、变体 CRUD、镜头表 CRUD、提示词冻结。
3. 生成与画布：单镜头生成、批量生成、生成状态、画布作用域加载。

所有长任务进入数据库任务队列，不允许依赖进程内状态。

## 8. 分阶段交付

### P0：模型冻结

- 确定对象、状态机、端口类型、三层画布边界。
- 输出数据库表结构和节点 JSON 契约。
- 验收标准：能用假数据渲染项目/剧集/镜头三级画布。

### P1：文稿到拆集

- 实现 `scriptInput`、`scriptFinalize`、`episodePlanner`。
- 支持 LLM 分块拆解和结构化校验。
- 验收标准：导入一个剧本后生成集数、每集梗概、场景和镜头草案。

### P2：资产库

- 实现角色、场景、道具资产卡及变体。
- 支持从拆解结果批量创建资产计划。
- 验收标准：一个项目能看到角色/场景/道具清单和跨集引用关系。

### P3：分镜与最终提示词

- 实现 `shotPlanner`、`promptComposer`。
- 支持提示词快照、差异对比、stale 传播。
- 验收标准：每个镜头能生成并冻结图片提示词和视频提示词。

### P4：图像到视频

- 复用现有图片/视频生成节点。
- 接入角色/场景引用和提示词版本。
- 验收标准：一个镜头可从角色场景资产生成关键帧，再生成视频，并回写到镜头。

### P5：批量生产

- 单集批量生成关键帧、批量生成视频、失败重试、任务队列。
- 项目看板显示缺失资产和完成率。
- 验收标准：三集 MVP 可完整跑到导出清单。

### P6：审核与交付

- 镜头采用版本、集级齐片检查、导出镜头表和素材清单。
- 验收标准：可交付一组采用版本的视频文件和对应提示词/资产引用记录。

## 9. 关键风险

1. LLM 一次性拆完整剧本容易超上下文：必须按“项目 → 集 → 场 → 镜头”分块执行。
2. 角色一致性是最大质量风险：角色必须先有设定卡和多视图参考，不能每镜头重新描述。
3. 资产变更会导致大量下游失效：必须做版本和 stale 标记。
4. 一个画布塞不下整季：从第一版就做三级画布，不要等节点超限再改。
5. 生成重试会产生大量记录：采用任务批次和幂等键，避免重复扣费和重复生成。
6. 不能为了快速验证引入 JSON 文件存储；数据库不可用时必须明确失败。

## 10. 建议的第一刀

先只做 P0，不碰真实生成：

- 冻结 8～9 张核心表。
- 冻结 9 个新节点的输入/输出契约。
- 冻结项目/剧集/镜头三层画布的数据结构和路由。
- 用一条示例剧本做静态原型，验证资产数量和交互是否合理。

P0 通过后，再实现 P1 的拆集，避免在模型还没稳定时先堆 UI 和生成逻辑。
